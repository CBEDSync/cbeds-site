# Working on this repo

A five-page static site for CBEDS at UCL, published to Netlify from `main`. No build
step, no framework, no database. Every page is hand-written HTML with its CSS and JS
inline; the only shared file is `cbeds-assistant.js`.

The people who run it are **not web developers**. Their instructions are in
`SUBMISSIONS.md` and `HOW-THE-SITE-WORKS.md` (plus `.docx` copies, because they read
them in Word). This file is the part they don't need: what will bite you.

---

## Things that break silently

These are ranked. The first two cause wrong data to be published with no error.

**1. `draft/CBEDSync.xlsx` is read by column position.** `build.py` maps fixed indices
per sheet — `row[7]` is an Agent's location, `range(21,28)` its theme flags, and so on.
Insert a column mid-sheet and every field after it shifts. The build will not complain;
it will publish a wrong graph. **New columns go at the far right.** `Source` and
`Show/Hide` are the two exceptions — found by heading via `find_col()`, so they can sit
anywhere.

**2. `cbedsync-data.js` is generated.** Never hand-edit it. Every `.bat` overwrites it.
If a change belongs in the data, it belongs in the workbook.

**3. The repository is public.** No key in any `.html`, `.js` or committed file. Keys
live in Netlify's environment variables and in a git-ignored `.env`.
`draft/Submissions.xlsx` is git-ignored because it holds names and email addresses —
check `.gitignore` before adding anything under `draft/`.

**4. `git checkout -- cbedsync-data.js` is the undo** for a local rebuild, and
`rebuild-only.bat` exists so data can be inspected before publishing. Don't run
`update-website.bat` on someone's behalf; it commits and pushes.

## The workbook cannot be round-tripped by openpyxl

`draft/CBEDSync.xlsx` has 28 parts: formulas on three sheets, three comment parts with
their VML drawings, 143 conditional-format rules and 8 data validations.
`openpyxl.load_workbook(...).save()`
drops most of that. Read-only mode is also unreliable for geometry — it renumbers sparse
rows, so neither `cell.column` nor `cell.coordinate` can be trusted.

**Read** with `openpyxl(read_only=True, data_only=True)` and take values by index only.
**Write** by editing the sheet XML inside the zip and copying every other part through
byte-for-byte. `pull-submissions.py:header_row_from_xlsx()` shows the read pattern; the
`Show/Hide` column (`f820898`) shows the write pattern. Two traps found the hard way:

- Excel does not commit to an attribute order in `xl/_rels/workbook.xml.rels` — some
  workbooks write `Id` first, some `Target` first. Parse each attribute separately.
- `<c/>` cells are self-closing. A regex that assumes `<c ...>…</c>` silently misses them
  and you will report a column as wrong when it is fine.

Always back the workbook up before writing, then verify: same part list, only the sheets
you meant changed, and Excel opens it without a repair prompt (`Excel.Application` COM
works for this).

`draft/Submissions.xlsx` is different — it is generated by openpyxl, so openpyxl may
freely round-trip it.

## Verifying in the browser

The preview pane in this environment is unreliable in specific ways. Knowing them saves
an hour:

- **Screenshots usually fail** ("the Browser pane is not displayed"). Measure geometry
  with `javascript_tool` instead — `getBoundingClientRect`, computed styles, offset
  parents. Say plainly in your report that you measured rather than looked.
- **`file://` pages render as a stale snapshot.** Edits do not appear. Use the dev server
  (`preview_start` with `{name: "site"}`, from the git-ignored `.claude/launch.json`) and
  load `http://localhost:8099/…`. If a CSS change seems not to apply, check the rule is
  actually in `document.styleSheets` before believing it.
- **CSS transitions on `grid-template-rows` do not resolve here.** A `0fr` → `1fr`
  collapse reports height 0 even when open. This made the Charter form look permanently
  broken. Test the mechanism in isolation before reporting a bug of that shape.
- Serving a PDF from the dev server triggers a download rather than a render.

## Netlify

Auto-deploys every push to `main`; `command = ""`, so it copies files as they are. About
a minute.

**Forms.** Both forms carry `data-netlify="true"`, a hidden `form-name` and
`netlify-honeypot="bot-field"`. Netlify strips those attributes at deploy after
detection, so a form only registers once a deploy has carried it — allow the full minute
before testing. `pull-submissions.py` reads them through the API: `/sites` to resolve the
internal site id from the domain, then `/sites/{id}/forms`, then
`/forms/{id}/submissions`.

**What is already collected is remembered in the spreadsheet**, in a
`Review: Netlify id` column — not in Netlify. So clearing the Netlify list is safe, but
deleting a staged row by hand brings it back on the next run while it is still in
Netlify, and loses it for good once it isn't.

**The function.** `netlify/functions/ask.mjs` is the only server code. It holds the key
and adds an AI gloss per section; without a key the page falls back to its own answers,
so nothing breaks. The LLM is constrained to name only entities present in the subgraph —
keep that constraint if you touch the prompt. Run `node scripts/smoke-ask.mjs` before
pushing changes to it; `node --check` will not catch a bad variable name inside the
handler.

## Conventions

**Commit only when asked, and push only when asked.** Both are said explicitly here.

Commit subjects are a sentence saying what changed for the reader, not a category —
"Stop the closed Charter form leaving 1,737px of blank page", not "fix(css): ...". The
body explains *why*, and names the failure if there was one. End with:

```
Co-Authored-By: Claude Opus 5 <noreply@anthropic.com>
```

Code comments follow the same rule: explain the reason, especially where the obvious
approach was wrong. There are several in this codebase that will stop you re-breaking
something — read the ones near whatever you are changing.

Copy on the site is plain, direct and second person. No marketing register.

PowerShell wraps anything git writes to stderr in a red `NativeCommandError`. A push that
prints `abc123..def456  main -> main` succeeded; check `git status -sb` rather than the
exit noise.

## Known loose ends

- `_to_delete/` holds 10 tracked files (old workbook and page snapshots). Flagged, never
  agreed for removal.
- `cbedsync-data.backup.js` is tracked and referenced by nothing.
- **GitHub Pages is still enabled on the repo** and its builds fail, emailing the owner on
  every push. Only they can turn it off: Settings → Pages → Source → None.
- `HERO_CAP` in `cbedsync.html:748` caps the hero preview at 428/150/753/33. The workbook
  now holds 1,596 entities, so the cap is behind the data.
- The privacy wording on both forms has not had UCL sign-off.
- 36 names are shared by two entries (usually a company and its product). Legitimate, and
  the build reports it every run — but a relation naming one of a pair reaches only the
  first. Nodes are laid out by `uid` rather than name so they no longer overlap.
